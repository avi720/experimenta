# AGENTS.md — experimenta

Guidance for coding agents working in this repository. Claude Code reads it through the
one-line `CLAUDE.md` next to it (`@AGENTS.md`); every nested `AGENTS.md` needs the same
companion — add one whenever you add a nested `AGENTS.md`.

Vite + React app on Supabase (Postgres + Auth), deployed on Vercel. Both CLIs are linked to this project (`vercel` → `experimenta`, `supabase` → ref `freuxiuhqjbtwolzyadc`).

A bilingual (Hebrew-first, English) virtual physics lab: guests browse and run the simulations,
signed-in users save runs and review them on Results, admins edit the experiment catalogue.
The app was originally generated by Base44; CI fails on any remaining `base44` reference.

**Mission: make real, hands-on physics experiments available to anyone, anywhere, without needing
a physical lab.**

Purpose and audience (full text in `README.md`): a replacement for school physics labs, used by
high-school and university students and curious people of all ages, including children. What this
means for changes:
- Physics must be correct. Users submit exported data in school assignments, so engine output,
  units and exported values must match the textbook formulas (covered by the engine tests).
- UI copy must work for a non-expert reader; explain physics terms instead of assuming them.

## Commands

| Command | What it does |
| --- | --- |
| `npm run dev` | Vite dev server on `http://localhost:5173` (`.claude/launch.json` config `dev`) |
| `npm run lint` | ESLint over `src`, **zero warnings allowed** |
| `npm run typecheck` | `tsc` strict over `src` (all of `src/` is TypeScript; no `allowJs`) |
| `npm run test:run` | Vitest once; `npm test` is watch mode |
| `npx vitest run src/simulation/engines/shoEngine.test.ts` | Run a single test file |
| `npx vitest run -t "key parity"` | Run tests whose name matches |
| `npm run build` | Production build into `dist/` |

CI (`.github/workflows/ci.yml`) runs lint → typecheck → test:run → build on pushes to `main`/`dev`
and on PRs, with placeholder `VITE_SUPABASE_*` values — tests must not hit the network.
Tests are colocated as `*.test.ts` next to the code they cover.

## Architecture

**Shell & routing.** `src/App.tsx` nests ErrorBoundary → QueryClientProvider → Router →
`AuthProvider` → `I18nProvider`. Routes use PascalCase page paths (`/Lab`, `/Results`,
`/AdminExperiments`; constants in `src/routes.ts`). Every page except Dashboard is `lazy()`-loaded.
`ProtectedRoute` gates by page name: `AUTH_REQUIRED_PAGES` need a session, `ADMIN_PAGES` need
`profiles.role = 'admin'`. Pages in `FULL_SCREEN_PAGES` (workspace, admin form) render full-height
without the site header (`src/Layout.tsx`); each page sits in its own ErrorBoundary.

**Experiments = DB template + registry entry.** An experiment is a row in `experiment_templates`
(parameters, presets, localized texts, `engine`, `slug`, `access_level`) plus one entry in
`src/simulation/experimentRegistry.ts`, which maps the template's `engine` key (or `slug`) to a pure
engine function and a lazy-loaded three.js scene. There is a single generic experiment page,
`LabWorkspace` (`/LabWorkspace?id=<slug>`); legacy `/FreeFallExperiment`-style URLs are derived from
the registry's `legacyPageName`. Adding an experiment needs no route or page edits.

**Simulation pipeline.** Engines in `src/simulation/engines/` are pure functions, unit-tested
against physics formulas. Registry `mode: "time"` engines are step functions
(`calculateStepFn(params, t)` → sample) driven by `useSimulationEngineLogic` (sample-dt choice,
`MAX_SAMPLES` cap) and `useSimulationManager` (playback/status); `mode: "static"` engines
(double slit) compute once via `calculateStaticFn`. `useExperimentSimulation` is the one hook a
page uses — it composes parameters/presets (`useExperimentParameters`), validation
(`src/simulation/parameterValidation.ts`, driven by the template's parameter `min`/`max`/`type`),
the run loop, and save/export (`useExperimentPersistence`). Scenes share setup and camera code
in `src/simulation/sceneUtils.ts` and `src/simulation/controls/`, and must dispose their renderer
and GPU resources on unmount.

**Data layer.** `src/entities/createEntity.ts` wraps a Supabase table in a small Base44-style API
(`list('-created_date', limit)`, `filter`, `get`, `create`, `update`, `delete`); entities are
exported from `src/entities/all.ts`. Components never call these directly for reads — they use the
TanStack Query hooks in `src/hooks/useDataQueries.ts` (one cached query per table, keys in
`appQueryKeys` from `src/lib/query-client.ts`); writes go through the mutation hooks there, which
invalidate the matching key. Row types come from the generated `src/types/database.ts` via
`src/types/models.ts`. Authorization lives in RLS: inactive and premium templates are hidden by
policy, runs are private to their owner; `src/lib/access.ts` only mirrors the access tiers in the UI.

**Auth.** `src/lib/AuthContext.tsx` holds the Supabase session plus the `profiles` row
(`role`, `subscription_tier`, `locale_preference`); guests' language choice lives in localStorage.

**i18n.** Custom, no library: dictionaries in `src/i18n/he.ts` and `src/i18n/en.ts`, accessed with
`const { t, dir, isRTL } = useTranslation()`. A test enforces 100% key parity, so every new string
needs both languages. Locale resolution: user profile → guest localStorage → `app_settings.locale_default`
→ Hebrew. Layouts must work in RTL (`dir`). Per-experiment content is localized inside the
template's JSON (`i18n_texts.he/en`, `i18n_labels`, `name_he/name_en`), not in the dictionaries —
read it with `pickLocalized(source, locale)`. `I18nProvider` is the single owner of `<html lang/dir>`.

**UI.** Tailwind + shadcn/ui primitives in `src/components/ui/` (excluded from lint; edit sparingly).
Page-specific components live under `src/components/pagesComponents/<page>/`. Import via the `@/`
alias for `src/`. Toasts use `sonner`; charts use `recharts`.

**History.** `docs/TECH-DEBT.md` is the completed audit (T1–T71, each mirrored as a GitHub Issue).
Code comments like `(T30)` point to its findings and explain why the code is shaped that way.

## Branching — `dev` is the working branch

- `main` = production (Vercel deploys it). Never commit or push to `main` directly.
- `dev` = active development branch. Commit and push work directly on `dev` (`origin/dev`), verify all changes locally (`npm run dev` → `http://localhost:5173`, `npm run lint`, `npm run build`, `npm run test:run`), and once verified open a PR from `dev` → `main` for release.
- Every UI change is verified in a browser on the local dev server (`npm run dev` → `http://localhost:5173`) before opening a PR to `main`. Production is not a test environment.
- Note: `Closes #N` in a commit or PR closes the issue when merged into `main`.

## QA test user

- A dedicated QA account (admin role) exists for browser checks of signed-in and admin pages.
- Its credentials live only in the gitignored `.env.local` as `QA_USER_EMAIL` / `QA_USER_PASSWORD` — never commit them (the repo is public).
- Local dev (`npm run dev`) and production share the same Supabase project, so this is a real production account: use it for read/verify flows and clean up any runs or templates you create.

## Database changes — migration files only

The schema's source of truth is `supabase/migrations/`. Never edit the production schema through the SQL editor or MCP `apply_migration`/`execute_sql` DDL.

1. `supabase migration new <short_name>` — creates a timestamped file.
2. Write idempotent-friendly SQL in it (RLS policies for every new table).
3. Review the plan: `supabase db push --dry-run`.
4. Apply: `supabase db push` (ask the user before pushing to production).
5. Commit the migration file together with the code that needs it.

- `supabase db pull` / `db diff` need Docker, which is not installed on this machine — write migrations by hand instead.
- The Supabase GitHub integration's "Deploy to production" and "Automatic branching" stay OFF (branching compute is billed outside the spend cap).
- Regenerate types after schema changes: `supabase gen types typescript --linked > src/types/database.ts`, then adjust `src/types/models.ts` if needed.
