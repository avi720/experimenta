## Background

experimenta is a bilingual (Hebrew-first, English) virtual physics lab. Visitors browse a catalogue of experiments, run interactive 3D simulations (free fall, simple harmonic oscillator, quantum tunneling, double slit), and signed-in users save runs and analyse them on a Results page; admins edit experiment templates through an in-app form. The app was generated by the Base44 AI builder and recently migrated to a Vite + React SPA on Supabase (Postgres + Auth) deployed on Vercel. It is a single-owner project with no tests and a CI that only lints and builds.

**Scope:** All application code under `src/`, the Supabase baseline migration, build/lint/CI tooling and npm dependencies. Out of scope: visual design and UX copy (no UI audit exists yet), shadcn component internals under `src/components/ui/` (only their usage is audited), and Supabase/Vercel dashboard settings that are not represented in the repo.

**Stack reviewed:** React 18 · Vite 6 · Tailwind 3 · shadcn/ui (Radix) · TanStack Query 5 · React Router 6 · three.js 0.171 · recharts 2 · Supabase JS 2 · Vercel · GitHub Actions.

**Methodology:**
1. Full source read in three parallel passes: (a) the simulation layer — `src/components/hooks/simulation/**`, the per-experiment hooks, `src/components/simulation/**` and the four experiment pages; (b) data, auth and admin — `src/api`, `src/entities`, `src/lib`, the admin hooks/pages/components, `src/pages/Results.jsx`, `supabase/migrations/20261022073402_baseline_schema.sql`; (c) app shell, routing, content pages, layout, dependencies and tooling.
2. Every "unused" / "dead" claim was checked with a repo-wide grep for importers before being recorded.
3. A clean copy of `HEAD` was installed with `npm ci` and run through `npm run lint`, `npm run build` (also with `--logLevel info`), `npm run typecheck`, `npm audit --omit=dev` and `npm outdated`.
4. The simulation engines and hooks were executed in plain Node with React stubbed, to measure data-point counts and compare physics output against textbook formulas.
5. Production (https://experimenta-sigma.vercel.app) was exercised in a browser for the SHO and Free Fall pages; those findings are marked **Confirmed.**
6. Each item scored with `Priority = (Impact + Risk) × (6 − Effort)`, all on a 1–5 scale, to order findings within a phase.

**Reference frameworks:** React rules of hooks & effect cleanup guidance · TanStack Query conventions · three.js disposal guide · Supabase RLS best practices · OWASP Top 10 (A01 access control, A06 vulnerable components) · 12-Factor App (config).

## How to Use This Plan

- Each finding is **outcome-driven**: it states what is wrong and what "fixed" looks like, but **not** how to implement it. The implementer chooses the approach.
- Work top-down by phase. **Do not skip Phase 1.** Phase 1 contains issues that block the next release — today three of the four experiment pages do not produce a working simulation.
- Phase 1 fixes the simulation pipeline in place. Phase 2 (T17–T19) then replaces the four copy-paste experiment pages with one generic page; if the owner answers Open Question 1 with "yes" before Phase 1 starts, T1–T5, T9 and T11–T14 can be satisfied directly by that rewrite — the Acceptance clauses still apply unchanged.
- A phase holds **at most 15 findings** so each milestone stays focused. When a phase would exceed that, move the lowest-priority items to the next phase (or a new one) rather than growing it. T-numbers stay global and do not change when an item moves, so a phase may list them out of order. (Rebalanced 2026-10-25: the old Phase 2/3 were split into Phases 2–5.)
- Tick the box only when the **Acceptance** clause is satisfied — not when the change is merely written.
- When an item lands, flip `[ ]` → `[x]` on the heading line. Empty boxes mean unfinished; ticked boxes mean Acceptance met. This lets anyone (or any session) skim the file and trust the state without re-deriving what shipped.
- If a finding turns out to be invalid in context, leave the box unchecked and add a `~~strikethrough~~` note explaining why.
- If a finding is deferred by an owner decision (won't-fix this round), tick `[x]`, wrap the Acceptance line in `~~strikethrough~~`, and append a short note explaining the decision.
- Every finding is mirrored as a GitHub Issue (linked from its heading); the issue tracks status, the doc holds the detail. Close the issue with `Closes #N` in the same commit that ticks the box — never one without the other.
- New findings discovered during fixes go at the bottom under "Discovered During Remediation", then get their own issue by re-running the issue sync.
- The `Status` line at the top is maintained by `/execute-work-plan` — leave it alone while writing this doc, and don't flip it to COMPLETED until that skill (or the user) decides every item is closed for good.

## Strengths — What Already Works Well

Preserve these patterns when refactoring:

- **RLS is complete and server-enforced** in `supabase/migrations/20261022073402_baseline_schema.sql`: all 5 tables have RLS enabled, grants are revoked then granted per role, `is_admin()` is `SECURITY DEFINER` with `search_path=''`, `protect_profile_privileges` blocks self-promotion, and `experiment_runs` are scoped to `created_by` with `WITH CHECK` on insert/update. The admin checks in `src/App.jsx` are UX only — the database is the gate.
- **`src/lib/AuthContext.jsx`** guards overlapping sign-in/out profile loads with a request id, defers `loadProfile` out of `onAuthStateChange` as Supabase recommends, and handles `PASSWORD_RECOVERY`.
- **`ProtectedRoute` in `src/App.jsx:28-43`** waits for auth/profile before deciding, redirects to `/Login?redirect=…` with the path encoded, and declares auth/admin requirements in one place; `src/pages/Login.jsx` `safeRedirect` blocks open redirects.
- **`src/components/hooks/useAppData.jsx` + `src/lib/query-client.js`** — shared `appQueryKeys`, TanStack caching with `staleTime`, a `DEFAULT_SETTINGS` fallback, `<html lang/dir>` sync for portaled Radix menus, and entity `onChange` invalidation. This is the data-fetching pattern to standardise on.
- **Pure physics engines** in `src/components/simulation/engines/` are `(t, params) → point` closed-form functions (SHO covers under/critical/over-damped; free fall has an analytic linear-drag solution; quantum tunneling does explicit SI conversion with a `kappaL` overflow guard) — trivially unit-testable.
- **`useSimulationEngineLogic`'s contract** — pre-compute then play back, cooperative yield every 1000 steps, and a `shouldStop` flag per data point — is a sound generic engine design.
- **`src/components/simulation/scenes/ShoScene.jsx`** is the template for scenes: data/params in refs to avoid stale rAF closures, rAF cancelled on unmount, `ResizeObserver`, controls and renderer disposed.
- **Data-driven parameter UI** — `ParameterInput` + `ParameterControls` render straight from `experiment.parameters` (float/int/bool/select, i18n labels, units, min/max), matching the DB schema; the right foundation for a single generic experiment page.
- **`src/entities/createEntity.js`** strips read-only columns (`id`, `created_by`, timestamps) on write, and `User.updateMe` whitelists `EDITABLE_PROFILE_FIELDS` — defence in depth alongside the DB trigger.
- **`.github/workflows/ci.yml`** uses concurrency cancel, cached `npm ci`, placeholder `VITE_*` vars so builds need no secrets, and a cheap regression grep against "base44".

#### [x] T6. Quantum tunneling transmission is wrong for E > V0 ([#9](https://github.com/avi720/experimenta/issues/9))

1. **One generic experiment page?** Should the four experiment pages be replaced by a single page (e.g. `/lab/:slug`) driven by the template's `engine` column and a registry? This decides whether Phase 1 patches the four pages or Phase 2 (T18–T20) replaces them first.

3. **Is `access_level` real gating?** If `registered`/`premium` must be enforced, it needs a server-side policy and an admin field; if not, should the column and UI be removed? Should inactive templates be hidden from anonymous visitors? (T38, T39)
